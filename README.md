# CSCS — Catering Security Control System

Production web application that digitizes the paper IFCSF workflow for airport
catering security operations:

| Part | Checkpoint | Role |
| ---- | ---------- | ---- |
| A | Warehouse dispatch (vehicle search, seal, signature) | Warehouse PIC |
| B | AVSEC Post 2 verification | AVSEC Post 2 |
| C | AVSEC Post 6 verification | AVSEC Post 6 |
| D | SRA Warehouse / Aircraft delivery confirmation | Receiver |

Plus: QR pass scanned at every checkpoint, digital signatures, incident
escalation, supervisor dashboard, daily/monthly reports (PDF + Excel), and an
immutable audit trail.

## Stack

- **Next.js 15** (App Router, Server Actions) + TypeScript + TailwindCSS (shadcn-style UI)
- **Supabase**: PostgreSQL, Auth, Storage, Row Level Security
- **Vercel** for hosting

## Workflow guarantees (enforced in the database, not just the UI)

- Transaction numbers `CSCS-YYYY-000001` are generated by a Postgres trigger
  (per-year sequence — no duplicates, no client input).
- Part B → C → D may only be inserted in order; each insert advances the
  transaction status (`CREATED → POST2_APPROVED → POST6_APPROVED → COMPLETED`).
- Any incident insert forces status `ESCALATED` and freezes checkpoint processing.
- Part records and audit logs are **write-once** (UPDATE/DELETE blocked by triggers).
- Completed transactions cannot be modified — the only allowed change is
  escalation via an incident.
- Every INSERT/UPDATE/DELETE on core tables is captured in `audit_logs` with
  who / what / when / before / after.
- RLS restricts each role to its own part; only the supervisor sees audit logs
  and all users.

## Local setup

### 1. Supabase project

1. Create a project at [supabase.com](https://supabase.com).
2. Open the SQL Editor and run, in order:
   - `supabase/migrations/20260101000001_schema.sql`
   - `supabase/migrations/20260101000002_rls.sql`

   (Or with the CLI: `supabase link --project-ref <ref>` then `supabase db push`.)
3. In **Authentication → Providers**, keep Email enabled. Disable public
   signups (Authentication → Settings → "Allow new users to sign up" → off);
   accounts are created by the supervisor.

### 2. Environment

```bash
cp .env.example .env.local
```

Fill in from **Project Settings → API**:

- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY` (server-only; used for user management + seeding)
- `NEXT_PUBLIC_APP_URL`

### 3. Install, seed, run

```bash
npm install
node scripts/seed.mjs   # demo accounts + sample transactions in every state
npm run dev
```

Demo accounts (password `CSCS-demo-2026!`):

| Role | Email |
| ---- | ----- |
| Warehouse PIC | pic@cscs.local |
| AVSEC Post 2 | post2@cscs.local |
| AVSEC Post 6 | post6@cscs.local |
| Receiver | receiver@cscs.local |
| Supervisor | supervisor@cscs.local |

### 4. Quality gates

```bash
npm run type-check   # tsc --noEmit
npm run lint         # eslint (next/core-web-vitals + next/typescript)
npm run build        # production build
```

## Deployment (Vercel)

1. Push this repository to GitHub.
2. In Vercel: **New Project → Import** the repo (framework auto-detected).
3. Add the four environment variables from `.env.example`
   (set `NEXT_PUBLIC_APP_URL` to the production URL).
4. Deploy. Run the migrations against your production Supabase project before
   first use, then `node scripts/seed.mjs` (with production env vars) or create
   the first supervisor manually:

```sql
-- After creating the auth user in Supabase Dashboard → Authentication → Users:
insert into public.users (id, name, staff_id, email, role)
values ('<auth-user-uuid>', 'Your Name', 'SV-0001', 'you@company.com', 'supervisor');
```

### Production checklist

- [ ] Migrations applied (schema + RLS) — verify `select * from pg_policies;`
- [ ] Storage buckets `signatures` and `incident-photos` exist and are **private**
- [ ] Public signups disabled in Supabase Auth
- [ ] `SUPABASE_SERVICE_ROLE_KEY` set only as a server env var (never `NEXT_PUBLIC_`)
- [ ] First supervisor account created
- [ ] Camera access requires HTTPS — Vercel provides this by default
- [ ] Demo/seed accounts removed or passwords rotated

```
src/app/(app)/transactions/          List + search
src/app/(app)/transactions/new/      Part A
src/app/(app)/transactions/[id]/     Detail, QR pass, Part B/C/D, incident
src/app/(app)/incidents/             Incident log

src/app/(app)/admin/users/           Supervisor: user management
src/app/(app)/admin/audit/           Supervisor: immutable audit trail
```

## Notes

- Mutations use **Next.js Server Actions** (the App Router replacement for
  hand-rolled API routes); every action re-verifies the caller's role
  server-side, and the database enforces the same rules again via RLS +
  triggers (defense in depth).
- Signatures and incident photos live in private buckets and are rendered
  through 1-hour signed URLs.
- Supervisor "notification" is in-app: escalations surface on the dashboard
  (red card) and the incidents page. To add email/SMS, attach a Supabase
  Database Webhook or trigger on `incidents` insert.
